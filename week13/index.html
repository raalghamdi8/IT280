Interactive multimedia in a real-time engine

From 3D asset to interactive application: the game loop, input and feedback, user-interface design, usability and accessibility testing, and keeping inside the frame budget.

01 · Real-time engines

How a real-time engine works

Key terms · tap for Arabic

بنت الأسابيع 8–12 محتوى ثلاثي الأبعاد وصيّرته. وتطبيق الوسائط المتعددة التفاعلي يتيح للناس التفاعل معه: التجوّل في متحف، وتدوير منتج، والإجابة عن اختبار، وتشغيل صوت وفيديو. والمحرّكات الآنية مثل Unity وUnreal وGodot توفّر ما يحتاجه كل تطبيق: التصيير، والفيزياء، والصوت، وتشغيل الفيديو، والتحريك، والإدخال، والواجهة، والبناء لمنصات كثيرة.

وفي قلب كل محرّك حلقة اللعبة، وهي حلقة التصيير من الأسبوع 10 بعد أن كبرت: في كل إطار تقرأ الإدخال، وتحدّث حالة كل كائن، ثم تصيّر الإطار. وعند 60 إطارًا في الثانية لديها نحو 16.7 ms.

وينظّم Unity المشهد في كائنات (GameObjects)، كل منها حاوية مكوّنات: Transform (الموضع والدوران والمقياس)، وMesh Renderer، وLight، وCamera، وAudio Source، ونصوصك البرمجية بلغة C#. والدالة Update() تعمل مرة كل إطار، وStart() مرة في البداية. ولأن الإطارات تختلف مدتها تُضرب الحركة في Time.deltaTime (الثواني منذ الإطار السابق)، فيدور الجسم بالسرعة نفسها على حاسب سريع أو بطيء.

ويستخدم المقرر Unity 6.3 LTS (إصدار دعم طويل صدر في ديسمبر 2025 ومدعوم حتى ديسمبر 2027) مع خط التصيير الشامل (URP). ورخصتا Personal وEducation مجانيتان للطلاب.

مثال محلول · حركة مستقلة عن معدل الإطارات

  1. نص برمجي يدير نموذجًا 2° لكل إطار.
  2. عند 60 fps: 120° في الثانية؛ وعند 30 fps: 60° فقط.
  3. بدلًا من ذلك أدِر بمقدار rotateSpeed × Time.deltaTime مع rotateSpeed = 90.
  4. فيعطي كلا المعدلين 90° في الثانية.

ترجمة عربية مساندة للشرح. المرجع هو النص الإنجليزي، وهو لغة الاختبارات والبرامج.

Weeks 8–12 built and rendered 3D content. An interactive multimedia application lets people act on that content: walk through a museum, turn a product, answer a quiz, trigger sound and video. Real-time engines such as Unity, Unreal and Godot provide the parts every such application needs: rendering (Weeks 8–12), physics, audio (Week 5), video playback (Week 6), animation (Weeks 7 and 14), input, user interface and building for many platforms.

At the heart of every engine is the game loop, the render loop of Week 10 grown up: every frame it reads input, updates the state of every object, then renders the frame. At 60 frames per second the whole loop has about 16.7 ms.

Unity organises a scene as GameObjects, each a container of components: a Transform (position, rotation, scale; Week 9), a Mesh Renderer, a Light, a Camera, an Audio Source, and your own scripts written in C#. A script’s Update() method runs once per frame; Start() runs once at the beginning. Because frames take different amounts of time, movement is multiplied by Time.deltaTime (the seconds since the last frame), so an object turns at the same speed on a fast and a slow computer.

This course uses Unity 6.3 LTS (Long-Term Support, released December 2025 and supported until December 2027) with the Universal Render Pipeline (URP), which runs on PCs, phones, the web and VR. The Personal and Education licences are free for students.

Worked example · frame-rate-independent movement

  1. A script turns a model by 2° per frame.
  2. At 60 fps: 2 × 60 = 120° per second. At 30 fps: only 60° per second: the app behaves differently on a slower PC.
  3. Instead turn by rotateSpeed × Time.deltaTime with rotateSpeed = 90.
  4. At 60 fps: 90 × 1⁄60 = 1.5° per frame; at 30 fps: 3° per frame. Both give 90° per second.

02 · Interaction

Input, events and feedback

Key terms · tap for Arabic

التفاعل يعني أن يستجيب التطبيق للشخص: للمفاتيح والفأرة واللمس وأذرع التحكم والصوت ويد الواقع الافتراضي. وفي Unity 6 تعدّ حزمة Input System الطريقة المعيارية لقراءة الإدخال، إما مباشرة في الشيفرة (Keyboard.current وMouse.current) أو عبر إجراءات الإدخال (Input Actions) التي تسمّي ما يفعله المستخدم وتربطه بعدة أجهزة معًا، وتتيح للاعبين إعادة تعيين المفاتيح، وهو متطلب لإمكانية الوصول.

  • المعالجة المباشرة: اسحب لتدوير النموذج، واقرص للتكبير.
  • اختيار الأجسام في الفضاء الثلاثي: إسقاط شعاع (raycast) من الكاميرا عبر موضع الفأرة يخبر أي جسم أصاب.
  • عناصر الواجهة: أزرار ومنزلقات ومفاتيح تبديل وقوائم.
  • المحفّزات: الدخول إلى منطقة يشغّل صوتًا أو فيديو.

وكل إجراء يحتاج تغذية راجعة خلال نحو 0.1 s: زر يتغير لونه، وجسم محدّد يُحاط بإطار، وصوت يؤكد. ودونها يكرّر المستخدم الإجراء أو يظن أن التطبيق توقف.

تحقّق من فهمك: في متحف افتراضي يضغط المستخدم على قطعة أثرية فلا يحدث شيء لثانيتين أثناء تحميل وصفها. ما التغييران المحسّنان؟

الإجابة: تغذية راجعة فورية (تمييز القطعة وإظهار مؤشر تحميل)، وتقليل الانتظار بتحميل الأوصاف مسبقًا.

ترجمة عربية مساندة للشرح. المرجع هو النص الإنجليزي، وهو لغة الاختبارات والبرامج.

Interaction means the application responds to the person: to keys, the mouse, touch, a controller, voice or a VR hand. In Unity 6 the Input System package is the standard way to read input. It can be read directly in code (Keyboard.current.spaceKey.wasPressedThisFrame, Mouse.current.delta) or through Input Actions, which name what the user does (“Rotate”, “Select”) and bind it to several devices at once: arrow keys, a gamepad stick and a touch drag can all drive the same action. Actions are also what lets players remap controls, an accessibility requirement.

Common interaction techniques in multimedia applications:

  • Direct manipulation: drag to rotate a model, pinch to zoom; the object follows the hand.
  • Selecting objects in 3D: a raycast shoots a ray from the camera through the mouse position (Week 10 in reverse) and reports which object it hits, so clicking an exhibit can show its information.
  • UI controls: buttons, sliders, toggles, menus (section 03).
  • Triggers: walking into an area starts a sound or a video.

Whatever the technique, every action needs feedback within about 0.1 s: a button changes colour when pressed, a selected object is outlined, a sound confirms. Without feedback users repeat the action or think the app has frozen.

In a virtual museum, users click an artefact but nothing seems to happen for two seconds while its description loads. What two changes would improve this?

Give immediate feedback (highlight the artefact and show a loading indicator at once), and reduce the wait, for example by loading descriptions in advance.

03 · User interface

Designing the user interface

Key terms · tap for Arabic

في Unity نظاما واجهة: uGUI يبني الواجهة من كائنات على لوحة (Canvas)، وUI Toolkit يبنيها من ملفات UXML وUSS الشبيهة بـHTML وCSS، وهو النظام الموصى به للواجهات الجديدة. ويستخدم اللاب uGUI لأنه أسهل تعلّمًا بصريًا؛ والمبادئ واحدة.

اضبط Canvas Scaler على Scale With Screen Size (المرجع 1920 × 1080) واستخدم نقاط الارتكاز لتثبيت العناصر في الأركان والحواف حتى يتكيّف التخطيط.

وأهم مبادئ نيلسن العشرة لقابلية الاستخدام في تطبيق صغير:

  • وضوح حالة النظام: أظهر ما يحدث (تحميل، تحديد، تشغيل).
  • مطابقة العالم الحقيقي: استخدم لغة المستخدمين وأيقونات مألوفة؛ وفي الواجهات العربية اعكس التخطيط من اليمين إلى اليسار.
  • تحكّم المستخدم وحريته: وفّر دائمًا طريق عودة: إعادة ضبط، تراجع، رجوع، تخطٍّ.
  • الاتساق: الإجراء نفسه يبدو ويعمل بالطريقة نفسها في كل مكان.
  • التعرّف لا التذكّر: اعرض عناصر التحكم على الشاشة.
  • التصميم البسيط: كل عنصر إضافي ينافس المحتوى؛ وقاعدة 60-30-10 للألوان تنطبق على الواجهات.
خطأ شائع

وضع عناصر الواجهة بمواضع بكسلات ثابتة لحجم شاشة واحد؛ فتتداخل الأزرار أو تخرج من الشاشة بدقة أخرى. استخدم نقاط الارتكاز واختبر بعدة دقات.

ترجمة عربية مساندة للشرح. المرجع هو النص الإنجليزي، وهو لغة الاختبارات والبرامج.

Unity has two UI systems. uGUI (Unity UI) builds interfaces from GameObjects on a Canvas: Buttons, Toggles, Sliders and TextMeshPro text, laid out in the Scene view. UI Toolkit builds them from UXML and USS files, similar to HTML and CSS, and is Unity’s recommended system for new runtime UI and editor tools. The lab uses uGUI because it is quicker to learn visually; the design principles are the same.

Screens differ in size and shape. Set the Canvas Scaler to Scale With Screen Size (reference 1920 × 1080) and use anchors to pin elements to corners or edges, so the layout adapts from a laptop to a projector. Remember the aspect-ratio lessons of Weeks 6 and 10.

Good interfaces follow a few well-tested principles, summarised in Jakob Nielsen’s ten usability heuristics. The ones that matter most in a small multimedia app:

  • Visibility of system status: show what is happening (loading, selected, playing).
  • Match the real world: use the users’ words and familiar icons; in Arabic interfaces, mirror the layout right to left.
  • User control and freedom: always offer a way back: Reset, Undo, Back, Skip.
  • Consistency: the same action looks and works the same everywhere.
  • Recognition rather than recall: show the controls on screen (“Drag to rotate · R to reset”) instead of expecting users to remember them.
  • Minimalist design: every extra element competes with the content. The 60-30-10 colour rule of Week 3 applies to UI too.
Common mistake

Placing UI with absolute pixel positions for one screen size. On a different resolution, buttons overlap or fall off screen. Use anchors and Scale With Screen Size, and test in the Game view at several resolutions.

04 · Usability testing

Testing with real users

Key terms · tap for Arabic

المصمّمون يعرفون منتجهم أكثر من اللازم فلا يرون مشكلاته. واختبار قابلية الاستخدام يراقب أشخاصًا حقيقيين يحاولون استخدامه. والاختبار الصغير رخيص ويكشف أكثر المشكلات الخطيرة:

  1. اكتب 3–5 مهام واقعية بصيغة أهداف لا تعليمات: «اعرف مادة القطعة اليسرى» لا «اضغط زر المعلومات».
  2. اختر مستخدمين يشبهون الجمهور الحقيقي (لا زملاء فريقك). نحو خمسة مستخدمين في كل جولة يكشفون أكثر المشكلات الكبرى؛ أصلحها ثم اختبر ثانية.
  3. التفكير بصوت عالٍ: اطلب من كل مستخدم أن يقول ما يفكر فيه أثناء العمل. لا تساعد ولا تشرح؛ وإن سأل فقل: «ماذا كنت ستفعل لو لم أكن هنا؟».
  4. سجّل نجاح كل مهمة وزمنها وكل مشكلة مع اقتباس أو ملاحظة.
  5. صنّف الخطورة (مثلًا 1 شكلية، 2 بسيطة، 3 كبيرة، 4 تمنع إتمام المهمة) وأصلح الأخطر أولًا.

ويضيف استبيان قصير رقمًا للمقارنة بين النسخ: مقياس قابلية استخدام النظام (SUS) عشر عبارات معيارية تقيَّم من 1 إلى 5 ويعطي درجة من 0 إلى 100؛ والمتوسط نحو 68.

تحقّق من فهمك: مجموعة طلبت من زميلين اختبار تطبيقها بعد شرح كل شاشة لهما، فأتمّا كل المهام. لماذا قد يكون الاختبار مضلّلًا؟

الإجابة: الشرح كشف ما يجب أن يكون واضحًا بذاته، والزملاء ليسوا مستخدمين نموذجيين؛ فقد يفشل مستخدمون حقيقيون في المهام نفسها.

ترجمة عربية مساندة للشرح. المرجع هو النص الإنجليزي، وهو لغة الاختبارات والبرامج.

Designers know too much about their own product to see its problems. Usability testing watches real people try to use it. A small test is cheap and finds most serious problems:

  1. Write 3–5 realistic tasks, phrased as goals, not instructions: “Find out what the artefact on the left is made of”, not “Click the Info button”.
  2. Recruit users like the real audience (not your teammates). About five users per round reveal most of the major problems; fix them, then test again.
  3. Think aloud: ask each user to say what they are thinking while they work. Do not help or explain; if they ask, reply “What would you do if I weren’t here?”.
  4. Record whether each task succeeded, how long it took, and every problem with a quote or observation.
  5. Rate severity (for example 1 = cosmetic, 2 = minor, 3 = major, 4 = blocks the task) and fix the worst first.

A short questionnaire adds a number you can compare between versions. The System Usability Scale (SUS) has ten standard statements rated 1–5 and gives a score from 0 to 100; about 68 is average. The Group Project test report uses these methods.

A group asks two classmates to test their app, explaining each screen before the classmates start. Both complete every task. Why might this test be misleading?

The explanations gave away what the app should make obvious, and teammates or friends are not typical users. Real users with no explanation might fail the same tasks.

05 · Accessibility

Designing for everyone

Key terms · tap for Arabic

إمكانية الوصول تعني أن يستطيع ذوو الإعاقة استخدام التطبيق: المكفوفون وضعاف البصر، ومصابو عمى الألوان، والصمّ وضعاف السمع، ومحدودو الحركة، وذوو الفروق الإدراكية. وهي تفيد الجميع: التعليقات النصية تفيد في المعامل الصاخبة. وإرشادات WCAG 2.2 من W3C كُتبت للويب لكن مبادئها تنطبق على أي واجهة: أن يكون المحتوى قابلًا للإدراك وللتشغيل وللفهم ومتينًا.

  • التباين: النص العادي يحتاج نسبة تباين 4.5 : 1 على الأقل مع خلفيته؛ والنص الكبير وعناصر الواجهة الرسومية 3 : 1 على الأقل. افحص بالحاسبة التفاعلية.
  • لا تعتمد على اللون وحده: الأحمر/الأخضر غير مرئي لكثير من مصابي عمى الألوان؛ أضف أيقونة أو كلمة.
  • تعليقات نصية لكل كلام وصوت مهم (الأسبوع 6)، وإشارات مرئية للأحداث الصوتية.
  • بدائل لوحة المفاتيح وذراع التحكم للسحب بالفأرة، وإعادة تعيين المفاتيح، وتجنّب الإجراءات التي تتطلب توقيتًا سريعًا دقيقًا.
  • نص مقروء بحجم كافٍ على الشاشة المستهدفة وقابل للتعديل.
  • الحركة والوميض: وفّر خيارًا لتقليل حركة الكاميرا، ولا تومض أكثر من ثلاث مرات في الثانية (خطر النوبات).

مثال محلول · تباين الأزرق في هذا المقرر على الأبيض

  1. الأزرق #2D5BC9 نصوعه النسبي L₁ ≈ 0.12، والأبيض L₂ = 1.
  2. النسبة = (L₂ + 0.05) ÷ (L₁ + 0.05) = 1.05 ÷ 0.17 ≈ 6.1.
  3. 6.1 ≥ 4.5، فالنص الأزرق على الأبيض مقبول.
  4. والكهرماني #E2A04A على الأبيض نحو 2.2 : 1: يصلح زينةً لا نصًا؛ ولهذا يستخدمه المقرر لونًا مميزًا بنسبة 10% فقط.

Accessibility means people with disabilities can use the application: people who are blind or have low vision, are colour-blind, deaf or hard of hearing, have limited movement, or have cognitive or attention differences. It also helps everyone else: captions help in noisy labs, large text helps on projectors. The Web Content Accessibility Guidelines (WCAG 2.2, W3C) were written for the web but their principles apply to any interface: content must be Perceivable, Operable, Understandable and Robust.

Concrete checks for a multimedia app:

  • Contrast: normal text needs a contrast ratio of at least 4.5 : 1 against its background; large text (about 24 px, or 19 px bold) and UI graphics such as button borders need at least 3 : 1. Check with the calculator below.
  • Never rely on colour alone: a red/green status is invisible to many colour-blind users; add an icon or a word.
  • Captions for all speech and important sounds (Week 6), and visual cues for audio events.
  • Keyboard and controller alternatives to mouse dragging; let users remap controls; avoid actions that need fast, precise timing.
  • Readable text: large enough on the target screen and adjustable where possible.
  • Motion and flashes: offer a way to reduce camera motion, and never flash more than three times per second (seizure risk).

Unity 6 also includes an accessibility API that exposes UI to screen readers on supported platforms; for this course the checks above are the requirement.

Worked example · contrast of this course’s blue on white

  1. Blue #2D5BC9 has relative luminance L₁ ≈ 0.12; white has L₂ = 1.
  2. Ratio = (L₂ + 0.05) ÷ (L₁ + 0.05) = 1.05 ÷ 0.17 ≈ 6.1.

06 · Performance

Performance: staying inside the frame budget

Key terms · tap for Arabic

التطبيق المتقطّع يبدو معطّلًا، وفي الواقع الافتراضي يسبب دوار الحركة. والهدف معدل إطارات ثابت: 30 أو 60 fps على الحواسيب والهواتف، و72–90 fps في الواقع الافتراضي. وكل شيء في الإطار يجب أن يتسع في ميزانية الإطار.

قِس أولًا. لوحة Stats تعرض معدل الإطارات والدفعات والمثلثات، وProfiler يعرض المللي ثواني لكل نظام وهل عنق الزجاجة في المعالج (CPU) أم وحدة الرسوميات (GPU). واختبر دائمًا نسخة مبنية على الجهاز المستهدف.

  • استدعاءات رسم أقل: شارك المواد، وادمج الأجسام الثابتة، ودع SRP Batcher والنسخ المتعدد على GPU يجمعانها.
  • مثلثات أقل: نماذج منخفضة المضلعات بخرائط متجهات مخبوزة (الأسبوع 12)، ومجموعات LOD تبدّل شبكات أبسط في البعيد.
  • خامات أصغر: اضغط الخامات (الأسبوع 4) واحتفظ بسلاسل Mipmap (الأسبوع 11).
  • إضاءة أرخص: اخبز الإضاءة الثابتة (الأسبوع 12) وقلّل الظلال الآنية.
  • ارسم أقل: الإقصاء خارج مخروط الرؤية تلقائي، وإخفاء المحجوب يتخطّى ما خلف الجدران.
  • النصوص البرمجية: تجنّب العمل الثقيل في Update() كل إطار.

مثال محلول · ميزانية الإطار

  1. الهدف 60 fps ← 1000 ÷ 60 = 16.7 ms.
  2. يُظهر المحلّل: النصوص 3 ms، والفيزياء 2 ms، والتصيير على المعالج 9 ms، وGPU 14 ms.
  3. مجموع المعالج 14 ms وGPU 14 ms: كلاهما ضمن الميزانية بهامش 2.7 ms فقط.
  4. التصيير يهيمن على وقت المعالج، فقلّل استدعاءات الرسم أولًا.
نموذج المشروع الجماعي الأولي يُسلَّم هذا الأسبوع

اعرض نموذجًا أوليًا عاملًا لتطبيقك التفاعلي في جلسة اللاب هذا الأسبوع: التفاعل الرئيسي يعمل من البداية إلى النهاية، مع أصول مؤقتة عند الحاجة. وأحضر خطة الاختبار (3–5 مهام) لاختبار قابلية الاستخدام الذي ستعرض تقريره في الأسبوع 15.

ترجمة عربية مساندة للشرح. المرجع هو النص الإنجليزي، وهو لغة الاختبارات والبرامج.

An app that stutters feels broken, and in VR it causes motion sickness. The target is a steady frame rate: 30 or 60 fps on PCs and phones (33.3 or 16.7 ms per frame), 72–90 fps in VR (13.9–11.1 ms). Everything in the frame (scripts, physics, animation, rendering) must fit in that frame budget.

Measure first. Guessing wastes time. Unity’s Stats panel (the Stats button in the Game view) shows fps, batches and triangles; the Profiler (Window › Analysis › Profiler) shows how many milliseconds each system takes and whether the CPU (scripts, physics, preparing draw calls) or the GPU (pixels, shaders, triangles) is the bottleneck. Always test a build on the target device; the Editor is slower than the final app.

Common fixes, linked to earlier weeks:

  • Fewer draw calls: each separate mesh and material is work for the CPU. Share materials, combine static objects, and let URP’s SRP Batcher and GPU instancing batch them.
  • Fewer triangles: low-poly models with baked normal maps (Week 12) and LOD groups that swap in simpler meshes far away.
  • Smaller textures: 4K textures on small props waste memory; compress textures (Week 4) and keep mipmaps (Week 11).
  • Cheaper lighting: bake static lighting into lightmaps (Week 12); limit real-time shadows and lights.
  • Draw less: frustum culling (Week 8) is automatic; occlusion culling also skips objects hidden behind walls.
  • Scripts: avoid heavy work in Update() every frame, such as searching the scene with GameObject.Find.

Worked example · the frame budget

  1. Target: 60 fps → 1000 ÷ 60 = 16.7 ms per frame.
  2. Profiler shows: scripts 3 ms, physics 2 ms, rendering on the CPU 9 ms, GPU 14 ms.
  3. CPU total = 14 ms and GPU = 14 ms: both fit, but with only 2.7 ms to spare.
  4. Rendering dominates the CPU time, so reduce draw calls first (share materials, enable batching) rather than optimising scripts.

ترجمة عربية مساندة للشرح. المرجع هو النص الإنجليزي، وهو لغة الاختبارات والبرامج.

Unity AI. Since Unity 6.2 (August 2025) the editor has an AI menu with three parts. Assistant is a project-aware chat that answers questions, writes and runs C#, batch-renames assets and places objects (it replaced Muse Chat). Generators create sprites, textures, materials, animations and sounds from prompts. Inference Engine (formerly Sentis) runs trained neural-network models locally, in the editor or inside your built app. Assistant and Generators run in Unity’s cloud and may need an account with AI access; Inference Engine runs on the user’s device.

AI at run time. Apps now use AI while the user is interacting: characters that answer in natural language through a large language model, voice commands through speech recognition, body or hand tracking from the camera. Each choice has a design cost that ties straight to this week. A cloud call that takes 1–3 seconds breaks the expectation of immediate feedback, so show the system’s status (Nielsen’s first heuristic). Every request costs money. Output is unpredictable, so you need guardrails (limits on what the character may say) and a fallback when the network fails. Users’ voices and images are personal data. On-device models avoid the network but must fit the 16.7 ms frame budget, or run on a background thread.

Accessibility. AI can draft alt text, captions and simple-language versions of instructions, which helps you meet WCAG. As with Week 6 captions, a person must check them.

Testing. Some teams ask AI to role-play users and spot obvious problems. That can catch a missing label, but it is not a usability test: the think-aloud sessions with five real users remain the evidence.

A group plans an NPC that answers each question by calling a cloud language model. Which two usability problems should they design for?

Delay: show that the character is “thinking” and keep the interface responsive (visibility of system status). Failure: handle no network or an unsuitable answer with a clear fallback message and guardrails (error prevention and recovery).

Week 13 in eight points

  1. An engine’s game loop reads input, updates objects and renders, every frame; Unity scenes are GameObjects with components.
  2. Multiply movement by Time.deltaTime so behaviour does not depend on frame rate.
  3. Unity 6 uses the Input System; Input Actions bind one action to many devices and allow remapping.
  4. Every action needs feedback within about 0.1 s; raycasts let users select objects in 3D.
  5. Build UI with anchors and Scale With Screen Size; follow the usability heuristics: status, control, consistency, recognition, minimalism.
  6. Usability testing: realistic tasks, ~5 representative users, think-aloud, record, rate severity, fix, retest; SUS gives a 0–100 score.
  7. Accessibility (WCAG): contrast ≥ 4.5 : 1 for text (3 : 1 large text and UI), never colour alone, captions, keyboard alternatives, no rapid flashing.
  8. Performance: fit the frame budget (16.7 ms at 60 fps); measure with Stats and the Profiler; reduce draw calls, triangles, texture size and real-time lighting.

    using UnityEngine;
using UnityEngine.InputSystem;

// Attach to the Main Camera. Drag your model into "Target".
public class ObjectViewer : MonoBehaviour
{
    public Transform target;          // the model to inspect
    public float rotateSpeed = 90f;   // degrees per second (keys)
    public float dragSpeed = 0.3f;    // degrees per pixel (mouse)
    public float zoomSpeed = 0.01f;   // metres per scroll unit
    public bool autoRotate = false;

    Quaternion startRotation;
    Vector3 startCameraPosition;

    void Start()
    {
        startRotation = target.rotation;
        startCameraPosition = transform.position;
    }

    void Update()   // runs once per frame
    {
        var keyboard = Keyboard.current;
        var mouse = Mouse.current;
        float yaw = 0f;

        if (keyboard != null)
        {
            if (keyboard.leftArrowKey.isPressed || keyboard.aKey.isPressed)  yaw += rotateSpeed * Time.deltaTime;
            if (keyboard.rightArrowKey.isPressed || keyboard.dKey.isPressed) yaw -= rotateSpeed * Time.deltaTime;
            if (keyboard.rKey.wasPressedThisFrame) ResetView();
        }
        if (autoRotate) yaw += 20f * Time.deltaTime;
        if (mouse != null && mouse.leftButton.isPressed)
            yaw -= mouse.delta.ReadValue().x * dragSpeed;

        target.Rotate(0f, yaw, 0f, Space.World);

        if (mouse != null)
            transform.position += transform.forward * mouse.scroll.ReadValue().y * zoomSpeed;
    }

    public void ResetView()               // called by the Reset button
    {
        target.rotation = startRotation;
        transform.position = startCameraPosition;
    }

    public void SetAutoRotate(bool on)     // called by the Auto-rotate toggle
    {
        autoRotate = on;
    }
}
    Drag the script onto the Main Camera. In the Inspector, drag your model from the Hierarchy into the Target field.
